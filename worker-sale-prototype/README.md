# تحضير محلي لمسار مبيعات لمسة عبر Cloudflare Worker

**الحالة:** تغييرات القطع وتهيئة العداد واختبارات الطابور أُعدت على فرع مراجعة PR #6؛ لم تُدمج أو تُنشر. لم تُنشأ مفاتيح/أسرار، ولم يُنشر Worker أو Pages، ولم تُكتب بيانات إنتاج أو تُغيّر قواعدها أو Billing. يوجد مانع تصميمي في طابع وقت بيع المالك ويوم العمولة؛ لذلك لا يُنشأ مفتاح ولا يُنشر المسار حالياً.

## ما أُنجز محلياً

- استبدال `TEST_PUBLIC_JWK` بتحقق Firebase ID token الفعلي: RS256، مطالبات Firebase/Google، وفحص `iat` و`auth_time`؛ الشهادات العامة تُخزّن مؤقتاً وفق `Cache-Control`. الاختبارات تستخدم خادم X.509 محلياً.
- إضافة OAuth 2.0 بحساب خدمة لـFirestore REST. العامل يوقّع JWT قصير العمر من binding وقت التشغيل، يطلب نطاق `https://www.googleapis.com/auth/datastore`، ويخزّن access token مؤقتاً في الذاكرة. لا يُحفظ المفتاح داخل المشروع.
- تثبيت قائمة سماح الموارد غير السرية في `src/productionConfig.mjs` على مشروع التطبيق `gen-lang-client-0515786951` وقاعدة Firestore المسماة `ai-studio-remixremixremixr-0f36aa66-a2c8-4d8a-bad2-ea0f72310677` وهوية الخدمة `firestore-store-worker@gen-lang-client-0515786951.iam.gserviceaccount.com`. القيم التشغيلية تأتي من `[env.production.vars]` في Wrangler، ويطابقها الحارس قبل تكوين أي مسار REST.
- إعداد الإنتاج يبقى مغلقاً بعلمين مستقلين: `FIRESTORE_PRODUCTION_TRANSPORT_ENABLED=false` و`SALE_WORKER_PRODUCTION_ENABLED=false`. وجود المتغيرات لا يفتح البيع. يلزم مفتاح runtime خارج Git ثم تفعيل منفصل بعد المراجعة.
- `/health` يعيد `{ok:true}` فقط عند صلاحية إعداد البيئة، دون إظهار البيئة أو المشروع أو المفتاح، ودون اتصال أو قراءة/كتابة إلى Firestore. عند نقص الإعداد يعيد `{ok:false}` فقط. اختبارات health تستبدل الشبكة وتثبت عدم إجراء أي طلب.
- اختبار quote وcommit كامليْن عبر `createFirestoreTransport`: مفتاح RSA مؤقت للاختبار، تبادل OAuth مموّه، وتحويل داخلي لطلبات Firestore REST ذات الهدف المثبّت إلى Emulator على loopback. لا يستدعي الاختبار Google أو Firestore أو Cloudflare الحية.
- `wrangler.toml` يحتفظ بإعداد Emulator المحلي، ويضيف بيئة إنتاج باسم `lamsa-sales-worker` مع المشروع والقاعدة وهوية الخدمة والمالك وOrigin الخاص بـPages، مع بقاء علمي الإنتاج `false`. لا يوجد مفتاح أو secret أو Worker URL في الملف.
- `firebase.json` الجذري يحدد قواعد `firestore.rules` على قاعدة AI Studio المسماة التي يستخدمها التطبيق، لا قاعدة `(default)`. اختبار محلي يؤكد تطابق إعداد Firebase CLI مع `firestoreDatabaseId` في التطبيق. اختبارات قواعد Rules Emulator تستخدم مشروع اختبار، ولا تتصل بقاعدة الإنتاج.
- Worker يعتمد في البيع على إسقاطات السعر والتكلفة المنفصلة: `tarek_sale_products`, `tarek_sale_bottle_sizes`, `tarek_products`, `product_costs`, `cost_catalog/store-cost-inputs`, `operational_settings/store`, و`financial_admin/store`، لا على `products`, `bottleSizes` أو `settings/store` القديمة كمصادر موثوقة للبيع.
- بيع المالك يكتب ذرياً `sales`, `sale_operations`, `sale_costs`, `sale_financials` وعداد اليوم مع تحديث المخزون. الإسقاط التشغيلي لا يحتوي التكلفة/الربح/العمولة. كاتبات المنتجات والإعدادات والعبوات تحدّث الإسقاطات المطلوبة مع الحفاظ على المخزون canonical عبر معاملات.
- POS المالك يستمع إلى `commission_day_counters/{UTC-date}` بدلاً من جمع فواتير اليوم لتسعير العمولة. مع العداد الجاهز تحدث الفاتورة والمخزون والعداد ذرياً؛ عند غياب العداد أو تعارض generation يسجل البيع والمخزون ذرياً كـ`needs_owner_review` بعمولة وربح صفريين، دون كتابة counter أو إسقاط مالي. Worker يطبق السلوك نفسه على quote/commit لطارق. لا تدخل هذه العمليات في العمولة التلقائية حتى مراجعة المالك.
- bootstrap التاريخي للمالك مطلوب مرة عند غياب counter لكل يوم UTC: يقارن سجلّي `sales` و`sale_operations` ويزيل التكرار، ويقبل حتى 5,000 مستند في كل مجموعة؛ البيانات الملتبسة أو الأكبر تغلق المسار. أُضيف استدعاء إنتاجي صريح من واجهة المالك إلى Worker، لكن الخادمين والواجهة لم يُنشرا بعد.
- POS المالك يرفض عمداً أي فاتورة مؤرخة خارج يوم UTC الحالي؛ لا توجد تهيئة تاريخية آمنة لإعادة ترتيب عمولة الأيام السابقة، لذا هذه القدرة متوقفة fail-closed حتى تصميم واختبار خاص.
- Worker يرفض مسارات البيع والتهيئة الإنتاجية قبل `2026-10-17T00:00:00Z` (03:00 القاهرة). يهيئ تطبيق المالك العداد تلقائياً عند بلوغ الموعد إذا كانت جلسة المالك والصفحة مفتوحتين؛ وإذا كانت الصفحة مغلقة، يبدأ عند أول دخول للمالك بعد الموعد ويهيئ اليوم UTC الحالي فقط، لا الأيام السابقة. لا توجد مهمة خلفية. هذا لا يسجل بيعاً ولا يمس `lamsa_offline_queue_v1`.
- `TarekSafePOS` مركّب في مساحة طارق عند وجود منحة بيع فعالة. يستخدم عقد v3 الذي لا يرسل سعر/تكلفة/ربح/عمولة من العميل، ويحصل على Firebase ID token قبل quote/commit. عنوان الخادم يأتي من `VITE_LAMSA_SALE_WORKER_URL` ويحتاج `VITE_LAMSA_SALE_WORKER_ENABLED=true` في build الإنتاج؛ GitHub Pages workflow يوقف النشر إن لم تُضبط القيمتان. في التطوير لا يقبل إلا Worker المحاكي المحلي. قيم `.env.example` فارغة/معطّلة، لذلك لا يوجد endpoint إنتاجي في النسخة الحالية.
- سجل البيع التشغيلي الذي يراه الموظف منفصل عن بيانات التكلفة والمالية. العكس للمالك فقط مع سجل غير حاذف، وقواعد Firestore تمنع الحذف النهائي والتحديثات غير المسموحة.

## مانع إطلاق: وقت اعتماد بيع المالك

POS المالك ينشئ `sale.date` من ساعة الجهاز أو من إدخال رجعي، ثم `saleSync` يستخرج منها `commissionDayKey` قبل معاملة Firestore ويكتب الفاتورة والعداد والمخزون ذرياً. `serverTimestamp()` لا يعطي العميل قيمته إلا بعد اعتماد المعاملة؛ لذا إضافته كحقل `serverAcceptedAt` وحده لا يثبت يوم العداد داخل المعاملة ولا يمنع تاريخاً محلياً مزيفاً. استبدال `sale.date` بالطابع الخادمي سيغيّر معنى وقت البيع الأصلي، خصوصاً للمزامنة المتأخرة، ولا ينبغي فعله.

الطابور القديم `lamsa_offline_queue_v1` محفوظ كما هو ولا يقرأه التطبيق الجديد أو يعيد إرساله؛ طابور المالك الجديد يستخدم `lamsa_offline_queue_v2`، بينما طارق يستخدم outbox منفصلاً. لا يُنقل أي سجل قديم ولا يعاد وسمه أو تشغيله تلقائياً.

عولج الخطر محلياً باستخدام عينات Worker موثوقة مع ساعة monotonic، وتثبيت وقت الحدث منفصلاً عن `serverAcceptedAt`، وتعليق العمولة عند الانحراف أو غياب العداد مع استمرار البيع والمخزون. اختبارات Worker وFirestore Emulator تتحقق من هذا المسار؛ لا تثبت التشغيل الحي أو صلاحيات IAM. بوابات الإنتاج ما زالت معطلة افتراضياً، ولم يُنشأ مفتاح أو secret ولم يحدث نشر.

## إعداد البيئة الإنتاجية — محدد محلياً لكنه غير مفعّل

`wrangler.toml` يحدد المتغيرات العامة غير السرية للبيئة الإنتاجية. القيم التالية **إعداد محلي فقط**؛ العلمَان يظلان `false`، ولم يُنشأ Worker أو مفتاح أو secret ولم يحدث نشر:

```text
ENVIRONMENT=production
PROJECT_ID=gen-lang-client-0515786951
FIRESTORE_DATABASE_ID=ai-studio-remixremixremixr-0f36aa66-a2c8-4d8a-bad2-ea0f72310677
GCP_SERVICE_ACCOUNT_EMAIL=firestore-store-worker@gen-lang-client-0515786951.iam.gserviceaccount.com
OWNER_EMAIL=moh.mhran@gmail.com
FIRESTORE_PRODUCTION_TRANSPORT_ENABLED=false
SALE_WORKER_PRODUCTION_ENABLED=false
CORS_ALLOWED_ORIGIN=https://mohmhran5-jpg.github.io
```

المفتاح الخاص غير موجود في Git أو `wrangler.toml`؛ لا يُضاف إلا كـruntime secret بعد حل المانع. عنوان Pages `https://mohmhran5-jpg.github.io` هو Origin؛ المسار `/lamsa-perfume-pos-ai-studio/` لا يدخل في CORS. Worker URL غير معروف وغير منشور، وإعداد Wrangler لا ينشئ المورد ولا يفعّله.

آخر تحقق مرئي من صفحة IAM بتاريخ 2026-10-16 الساعة 06:25 أظهر ربط هوية الخدمة بالدور `projects/gen-lang-client-0515786951/roles/firestoreStoreReadWriteNoDelete` على مستوى المشروع، مع الصلاحيات الخمس:

- `datastore.databases.get`
- `datastore.entities.get`
- `datastore.entities.list`
- `datastore.entities.create`
- `datastore.entities.update`

لم تتضمن القائمة `delete`، ولم يُسجل تغيير لاحق للدور؛ والتنبيه اللاحق عن `delete` كان false positive من جمع أحداث منفصلة. نعتمد هذا التحقق السابق كما طلب المالك. لم يُنشأ مفتاح. هذه صلاحيات موارد Firestore وليست تقييداً دقيقاً للحقول؛ حساب الخدمة يستطيع قراءة البيانات المالية اللازمة لمعالجة المبيعات.

## الواجهة وما لا يزال غير مدعوم

- الواجهة الحالية تُظهر منتجاً مفرداً أو ميكس يدوياً من مكوّنين أو ثلاثة، أو وصفة محفوظة معتمدة من المالك، والعبوة والكمية، وعبوة ملوّنة عند إعداد سعر لها، خصماً يدوياً آمناً، أربعة عروض ثابتة، واختيار التغليف المعتمد كهدية أو بسعر ثابت، وطرق الدفع: نقدي/بطاقة/محفظة/تحويل. وصفة طارق المنقولة تعرض الاسم ومعرّفات المنتجات والجرامات والعبوة فقط، ولا تعرض التكلفة أو السعر المحفوظ؛ يعيد العامل التسعير والتحقق من المخزون وقت البيع.
- **ليست حية:** لا يوجد Worker منشور أو endpoint إنتاجي، وعميل الواجهة معطّل افتراضياً. لا تعمل مزامنة مبيعات حيّة بين المالك وطارق بعد. عميل bootstrap يمكنه استخدام endpoint الإنتاج عند ضبط البناء، لكنه لم يُنشر أو يُفعّل. إعداد CORS المحلي لا يعني أنه نُشر.
- لا توجد مبيعات جديدة دون اتصال للموظف. إذا انقطع الاتصال بعد quote، تُحفظ نية طارق في outbox `localStorage` على هذا المتصفح فقط، وتُعاد المحاولة بنفس معرف الفاتورة بعد عودة الاتصال. هذا يمنع التكرار على الجهاز ضمن شروط المتصفح، لكنه لا يزامن أجهزة متعددة، والتخزين غير مشفر وقد لا يمنع سباق التبويبات في fallback. أما طابور المالك القديم فيبقى كما هو ولا يُمسح.
- ما يزال غير مدعوم في مسار طارق/Worker الآمن: حملات العروض المخصصة بوصفها عروضاً مسماة، الوصول إلى سجلات CRM/العملاء، استبدال/كسب نقاط الولاء، تعديل الفاتورة أو حذفها نهائياً، ومؤشر إعادة شراء الخلطة. واجهات المالك الحالية لا تُحذف، لكن سجلات العملاء/النقاط تُحدّث بعد البيع منفصلة عن معاملة البيع ولا ينعكس أثر النقاط تلقائياً مع العكس. يستطيع طارق استخدام الخصم اليدوي الآمن والعروض الثابتة المعتمدة؛ لا توجد حملة مخصصة بمرجع وأهلية يثق بهما Worker. مؤشر المالك الحالي يقيس عودة العميل إلى أي شراء سابق، لا شراء التركيبة نفسها، ولا يعكس الإلغاء. لم تُخترع قواعد أو نقاط أو سياسات جديدة. الوصفات القديمة لا تُرحّل جماعياً؛ لا تظهر لطارق حتى يعيد المالك حفظ وصفة معتمدة. عكس الفاتورة للمالك فقط كسجل تدقيق؛ الحذف النهائي معطل.
- مزود Google Sign-In مفعّل وأُضيف مجال Pages إلى Authorized domains. ما زالت منحة بريد طارق في الإنتاج، ونشر قواعد القاعدة المسماة، وWorker وواجهة البناء أموراً غير مكتملة. لم تُختبر مزامنة طارق حياً.

راجع [QUOTA_AND_CAPACITY.md](./QUOTA_AND_CAPACITY.md) للتقديرات المفصلة والمصادر الرسمية. توضح وثيقة [Google AI Studio Starter Tier](https://cloud.google.com/blog/topics/developers-practitioners/the-starter-tier-for-google-ai-studio-explained) أن قواعد Firestore التي ينشئها AI Studio تتشارك: **40,000 كتابة/يوم، 50,000 قراءة/يوم، 50,000 تحديث لحظي/يوم، 1 GiB تخزين إجمالاً، و10 GiB نقل صادر شهرياً**. عند استنفاد حد يومي تتوقف قواعد المجموعة حتى قرابة منتصف الليل Pacific؛ لا توجد ضمانة سعة/توافر غير محدود.

## نتائج التحقق المحلي الحالية

- `npm run test:app-contract`: **33/33**، ويشمل CORS الدقيق، health دون اتصال أو كشف، حارس الإنتاج، قطع التاريخ، ومطابقة موارد Wrangler.
- `npm run test:prototype`: **33/33** عقود Worker، **17/17** تكامل Lamsa Emulator، و**15/15** فحوص auth/stream.
- `npm run lint` و`npm run build`: ناجحان؛ Vite ما زال يحذر من chunk أكبر من 500 KiB.
- `npm run test:security`: **69/69**.
- `npm run test:firestore`: **156/156** على Firestore Emulator، منها إثبات أن `serverTimestamp` لا يُقرأ قبل commit واختبار حفظ بيانات الطابور. الاختبار يؤكد أن Firebase CLI يستهدف القاعدة المسماة الصحيحة؛ قواعد الأمان نفسها تُختبر محلياً لا على قاعدة الإنتاج.

كل الاختبارات محلية أو mocks/Emulator فقط. لم تُسجّل مبيعات حقيقية ولم يُجر تغيير إنتاجي. الاختبارات لا تثبت IAM أو OAuth أو الحصص الحية، ولا تعني أن الموقع يعمل بمزامنة طارق.

## ما يلزم قبل أي نشر

1. التحقق السابق لخطة Workers Free في حساب Cloudflare `Offers` ولقطة IAM في 2026-10-16 06:25 يثبتان الخطة والدور المقصود؛ لا توجد حاجة لطلب تأكيد جديد. لا يوجد حالياً عامل لمسة، وWrangler المحلي غير مصادق.
2. **لا تنشئ مفتاحاً أو Cloudflare Secret ولا تنشر الآن:** مانع وقت بيع المالك ويوم العمولة والطابور الأوفلاين المذكور أعلاه يجعل مسار البيع المالي غير جاهز، حتى مع صلاحيات IAM والخطة المجانية.
3. يلزم اعتماد تصميم يضمن أن وقت اعتماد المالك و`commissionDayKey` ينشآن من توقيت خادمي داخل مسار موثوق، وسياسة واضحة للفواتير التي تعود من الطابور بعد تغير اليوم. أبقِ `lamsa_offline_queue_v1` كما هو؛ لا تمسحه أو تعِد وسمه أو تعاود تشغيله عشوائياً.
4. بعد حل ذلك واختباره فقط يمكن إنشاء الاعتماد المصرح به وحفظه مباشرة كـCloudflare Secret، ثم نشر Worker مستقل باسم `lamsa-sales-worker` على الخطة المجانية دون المساس بـ`offers`، ونشر قواعد قاعدة التطبيق المسماة وواجهة Pages. لا Billing/Blaze، ولا quote إنتاجي لأنه يكتب `sale_quotes`، ولا مبيعات اختبارية أو كتابة بيانات إنتاج.
