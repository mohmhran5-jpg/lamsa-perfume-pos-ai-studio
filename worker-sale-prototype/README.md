# تحضير محلي لمسار مبيعات لمسة عبر Cloudflare Worker

**الحالة:** الإعداد الإنتاجي محدد محلياً ومغلق افتراضياً، وغير منشور. لم تُنشأ مفاتيح/أسرار، ولم يُنشر Worker أو Pages، ولم تُكتب بيانات Firebase إنتاجية أو تُغيّر قواعدها أو إعدادات Billing. جرى فقط فحص قراءة محدود لخدمات الإدارة في هذه الجولة.

## ما أُنجز محلياً

- استبدال `TEST_PUBLIC_JWK` بتحقق Firebase ID token الفعلي: RS256، مطالبات Firebase/Google، وفحص `iat` و`auth_time`؛ الشهادات العامة تُخزّن مؤقتاً وفق `Cache-Control`. الاختبارات تستخدم خادم X.509 محلياً.
- إضافة OAuth 2.0 بحساب خدمة لـFirestore REST. العامل يوقّع JWT قصير العمر من binding وقت التشغيل، يطلب نطاق `https://www.googleapis.com/auth/datastore`، ويخزّن access token مؤقتاً في الذاكرة. لا يُحفظ المفتاح داخل المشروع.
- تثبيت قائمة سماح الموارد غير السرية في `src/productionConfig.mjs` على مشروع التطبيق `gen-lang-client-0515786951` وقاعدة Firestore المسماة `ai-studio-remixremixremixr-0f36aa66-a2c8-4d8a-bad2-ea0f72310677` وهوية الخدمة `firestore-store-worker@gen-lang-client-0515786951.iam.gserviceaccount.com`. القيم التشغيلية تأتي من `[env.production.vars]` في Wrangler، ويطابقها الحارس قبل تكوين أي مسار REST.
- إعداد الإنتاج يبقى مغلقاً بعلمين مستقلين: `FIRESTORE_PRODUCTION_TRANSPORT_ENABLED=false` و`SALE_WORKER_PRODUCTION_ENABLED=false`. وجود المتغيرات لا يفتح البيع. يلزم مفتاح runtime خارج Git ثم تفعيل منفصل بعد المراجعة.
- `/health` يعيد `{ok:true}` فقط عند صلاحية إعداد البيئة، دون إظهار البيئة أو المشروع أو المفتاح، ودون اتصال أو قراءة/كتابة إلى Firestore. عند نقص الإعداد يعيد `{ok:false}` فقط. اختبارات health تستبدل الشبكة وتثبت عدم إجراء أي طلب.
- اختبار quote وcommit كامليْن عبر `createFirestoreTransport`: مفتاح RSA مؤقت للاختبار، تبادل OAuth مموّه، وتحويل داخلي لطلبات Firestore REST ذات الهدف المثبّت إلى Emulator على loopback. لا يستدعي الاختبار Google أو Firestore أو Cloudflare الحية.
- `wrangler.toml` يحتفظ بإعداد Emulator المحلي، ويضيف بيئة إنتاج باسم `lamsa-sales-worker` مع المشروع والقاعدة وهوية الخدمة والمالك وOrigin الخاص بـPages، مع بقاء علمي الإنتاج `false`. لا يوجد مفتاح أو secret أو Worker URL في الملف.
- `firebase.json` الجذري يحدد قواعد `firestore.rules` على قاعدة AI Studio المسماة التي يستخدمها التطبيق، لا قاعدة `(default)`. اختبار محلي يؤكد تطابق إعداد Firebase CLI مع `firestoreDatabaseId` في التطبيق. اختبارات قواعد Rules Emulator تستخدم مشروع اختبار، ولا تتصل بقاعدة الإنتاج.
- Worker يعتمد في البيع على إسقاطات السعر والتكلفة المنفصلة: `tarek_sale_products`, `tarek_sale_bottle_sizes`, `tarek_products`, `product_costs`, `cost_catalog/store-cost-inputs`, `operational_settings/store`, و`financial_admin/store`، لا على `products`, `bottleSizes` أو `settings/store` القديمة كمصادر موثوقة للبيع.
- بيع المالك يكتب ذرياً `sales`, و`sale_operations`, و`sale_costs`, و`sale_financials` **وعداد اليوم** مع تحديث المخزون. الإسقاط التشغيلي لا يحتوي التكلفة/الربح/العمولة. كاتبات المنتجات والإعدادات والعبوات تحدّث الإسقاطات المطلوبة مع الحفاظ على المخزون canonical عبر معاملات.
- POS المالك يستمع إلى `commission_day_counters/{UTC-date}` بدلاً من جمع فواتير اليوم لتسعير العمولة. المعاملة تقارن `commissionCounterGeneration` الحالية وتحدّث العداد مع البيع أو العكس؛ أي generation قديمة أو عداد غير جاهز ترفض البيع قبل أي كتابة/خصم مخزون. سجل counter owner-only، والموظف لا يقرأه ولا يكتبه.
- bootstrap التاريخي للمالك مطلوب مرة عند غياب counter لكل يوم UTC: يقارن سجلّي `sales` و`sale_operations` ويزيل التكرار، ويقبل حتى 5,000 مستند في كل مجموعة؛ البيانات الملتبسة أو الأكبر تغلق المسار. bootstrap الحالي مقيد بالمحاكي، ولا يوجد مسار إنتاجي منشور.
- POS المالك يرفض عمداً أي فاتورة مؤرخة خارج يوم UTC الحالي؛ لا توجد تهيئة تاريخية آمنة لإعادة ترتيب عمولة الأيام السابقة، لذا هذه القدرة متوقفة fail-closed حتى تصميم واختبار خاص.
- `TarekSafePOS` مركّب في مساحة طارق عند وجود منحة بيع فعالة. يستخدم عقد v3 الذي لا يرسل سعر/تكلفة/ربح/عمولة من العميل، ويحصل على Firebase ID token قبل quote/commit. عنوان الخادم يأتي من `VITE_LAMSA_SALE_WORKER_URL` ويحتاج `VITE_LAMSA_SALE_WORKER_ENABLED=true` في build الإنتاج؛ في التطوير لا يقبل إلا Worker المحاكي المحلي. قيم `.env.example` فارغة/معطّلة، لذلك لا يوجد endpoint إنتاجي في النسخة الحالية.
- سجل البيع التشغيلي الذي يراه الموظف منفصل عن بيانات التكلفة والمالية. العكس للمالك فقط مع سجل غير حاذف، وقواعد Firestore تمنع الحذف النهائي والتحديثات غير المسموحة.

## إعداد البيئة الإنتاجية — محدد محلياً لكنه غير مفعّل

`wrangler.toml` يحدد المتغيرات العامة غير السرية للبيئة الإنتاجية. القيم التالية **إعداد محلي فقط**؛ العلمَان يظلان `false`، ولم يُنشأ Worker أو مفتاح أو secret ولم يحدث نشر:

```text
ENVIRONMENT=production
PROJECT_ID=gen-lang-client-0515786951
FIRESTORE_DATABASE_ID=ai-studio-remixremixremixr-0f36aa66-a2c8-4d8a-bad2-ea0f72310677
GCP_SERVICE_ACCOUNT_EMAIL=firestore-store-worker@gen-lang-client-0515786951.iam.gserviceaccount.com
OWNER_EMAIL=moh.mhran@gmail.com
FIRESTORE_PRODUCTION_TRANSPORT_ENABLED=false
SALE_WORKER_PRODUCTION_ENABLED=false
CORS_ALLOWED_ORIGIN=https://mohmhran5-jpg.github.io
```

المفتاح الخاص غير موجود في Git أو `wrangler.toml`؛ لا يُضاف إلا كـruntime secret بعد مراجعة وموافقة منفصلتين. عنوان Pages `https://mohmhran5-jpg.github.io` هو Origin؛ المسار `/lamsa-perfume-pos-ai-studio/` لا يدخل في CORS. Worker URL غير معروف وغير منشور، وإعداد Wrangler لا ينشئ المورد ولا يفعّله.

وفق سياق المشروع، هوية الخدمة أُنشئت وربطت بدور مخصص، لكن قائمة الصلاحيات الدقيقة **لم يتم التحقق منها عبر Google في هذه الجولة**. الصلاحيات المبلغ عنها للدور هي:

- `datastore.databases.get`
- `datastore.entities.get`
- `datastore.entities.list`
- `datastore.entities.create`
- `datastore.entities.update`

لا توجد صلاحية `delete` وفق التعريف المبلغ عنه. هذه صلاحيات على مستوى موارد Firestore وليست تقييداً دقيقاً للحقول؛ حساب الخدمة يستطيع قراءة البيانات المالية اللازمة لمعالجة المبيعات. الموافقة السابقة على الوصول المالي لا تعني موافقة على إنشاء مفتاح أو تخزين secret أو نشر Worker.

## الواجهة وما لا يزال غير مدعوم

- الواجهة الحالية تُظهر منتجاً مفرداً أو ميكس يدوياً من مكوّنين أو ثلاثة، أو وصفة محفوظة معتمدة من المالك، والعبوة والكمية، وعبوة ملوّنة عند إعداد سعر لها، خصماً يدوياً آمناً، أربعة عروض ثابتة، واختيار التغليف المعتمد كهدية أو بسعر ثابت، وطرق الدفع: نقدي/بطاقة/محفظة/تحويل. وصفة طارق المنقولة تعرض الاسم ومعرّفات المنتجات والجرامات والعبوة فقط، ولا تعرض التكلفة أو السعر المحفوظ؛ يعيد العامل التسعير والتحقق من المخزون وقت البيع.
- **ليست حية:** لا يوجد Worker منشور أو endpoint إنتاجي، وعميل الواجهة معطّل افتراضياً. لا تعمل مزامنة مبيعات حيّة بين المالك وطارق بعد. عميل bootstrap التاريخي ما زال مقيداً بالمحاكي. إعداد CORS المحلي لا يعني أنه نُشر.
- لا توجد مبيعات جديدة دون اتصال. إذا انقطع الاتصال بعد quote، تُحفظ النية في outbox `localStorage` على هذا المتصفح فقط، وتُعاد المحاولة بنفس معرف الفاتورة بعد عودة الاتصال. هذا يمنع التكرار على الجهاز ضمن شروط المتصفح، لكنه لا يزامن أجهزة متعددة، والتخزين غير مشفر وقد لا يمنع سباق التبويبات في fallback.
- ما يزال غير مدعوم في مسار طارق/Worker الآمن: حملات العروض المخصصة بوصفها عروضاً مسماة، الوصول إلى سجلات CRM/العملاء، استبدال/كسب نقاط الولاء، تعديل الفاتورة أو حذفها نهائياً، ومؤشر إعادة شراء الخلطة. واجهات المالك الحالية لا تُحذف، لكن سجلات العملاء/النقاط تُحدّث بعد البيع منفصلة عن معاملة البيع ولا ينعكس أثر النقاط تلقائياً مع العكس. يستطيع طارق استخدام الخصم اليدوي الآمن والعروض الثابتة المعتمدة؛ لا توجد حملة مخصصة بمرجع وأهلية يثق بهما Worker. مؤشر المالك الحالي يقيس عودة العميل إلى أي شراء سابق، لا شراء التركيبة نفسها، ولا يعكس الإلغاء. لم تُخترع قواعد أو نقاط أو سياسات جديدة. الوصفات القديمة لا تُرحّل جماعياً؛ لا تظهر لطارق حتى يعيد المالك حفظ وصفة معتمدة. عكس الفاتورة للمالك فقط كسجل تدقيق؛ الحذف النهائي معطل.
- تسجيل Google Sign-In ومجال Pages كانا مفعّلين/مصرحاً بهما في التحقق السابق؛ ما زالت منحة بريد طارق في الإنتاج، ونشر قواعد القاعدة المسماة، وWorker وواجهة البناء، وbootstrap المالك، وفحص IAM والسر أموراً غير مكتملة. لم تُختبر مزامنة طارق حياً.

## حدود الحصص

راجع [QUOTA_AND_CAPACITY.md](./QUOTA_AND_CAPACITY.md) للتقديرات المفصلة والمصادر الرسمية. توضح وثيقة [Google AI Studio Starter Tier](https://cloud.google.com/blog/topics/developers-practitioners/the-starter-tier-for-google-ai-studio-explained) أن قواعد Firestore التي ينشئها AI Studio تتشارك: **40,000 كتابة/يوم، 50,000 قراءة/يوم، 50,000 تحديث لحظي/يوم، 1 GiB تخزين إجمالاً، و10 GiB نقل صادر شهرياً**. عند استنفاد حد يومي تتوقف قواعد المجموعة حتى قرابة منتصف الليل Pacific؛ لا توجد ضمانة سعة/توافر غير محدود.

## نتائج التحقق المحلي الحالية

- `npm run test:app-contract`: **32/32**، ويشمل CORS الدقيق، health دون اتصال أو كشف، حارس الإنتاج، ومطابقة موارد Wrangler.
- `npm run test:prototype`: **32/32** عقود Worker، **17/17** تكامل Lamsa Emulator، و**15/15** فحوص auth/stream.
- `npm run lint` و`npm run build`: ناجحان؛ Vite ما زال يحذر من chunk أكبر من 500 KiB.
- `npm run test:security`: **67/67**.
- `npm run test:firestore`: **154/154** على Firestore Emulator. الاختبار يؤكد أن Firebase CLI يستهدف القاعدة المسماة الصحيحة؛ قواعد الأمان نفسها تُختبر محلياً لا على قاعدة الإنتاج.

كل الاختبارات محلية أو mocks/Emulator فقط. لم تُسجّل مبيعات حقيقية ولم يُجر تغيير إنتاجي. الاختبارات لا تثبت IAM أو OAuth أو الحصص الحية، ولا تعني أن الموقع يعمل بمزامنة طارق.

## ما يلزم قبل أي نشر

1. مراجعة diff في PR #6، خصوصاً قواعد Firestore وإعداد البيئة الإنتاجية، ثم موافقة منفصلة على أي نشر.
2. تصميم bootstrap إنتاجي للمالك على المحاكي، ومراجعة حد 5,000 سجل وسياسة نقطة القطع `2026-10-17T00:00:00Z` وخطة احتفاظ بوثائق quote.
3. بعد نشر مصرح به فقط، مراقبة الاستخدام الكلي لحصة AI Studio المشتركة؛ تجاوز الحد يوقف قواعد المجموعة، ولا يُستخدم ذلك مبرراً لتفعيل Billing/Blaze.
4. التحقق من دور IAM وصلاحياته من المصدر، ثم مراجعة إنشاء/حفظ المفتاح في Secret Store كقرار منفصل؛ لم يُنشأ أي مفتاح أو secret هنا.
5. عدم نشر Worker أو Pages أو تغيير Firebase Rules/بيانات الإنتاج ضمن هذه الجولة. تبقى كل بوابات الإنتاج مغلقة حتى مراجعة المستخدم وموافقته.
